# 组织、群聊与隔离：Aeloon 0.3 设计

状态：已确认，2026-09-07。承接 [design-colleagues.md](design-colleagues.md)。
那一轮定的「Agent 即同事、一位同事一条对话、没有工作区」仍然成立；这一轮把它从
单人扩展到组织，并加上群聊。本文是这次讨论的决策记录。

## 1. 部署与身份

- **一台服务器一个 Runtime，服务整个组织。** 没有租户，不按人分容器。Docker 降级为
  打包方式，systemd 单进程是唯一的服务端部署形态。`tenant init/add/...`、网关的 slug
  路由、group 容器整套删除。
- **不做密码，做「设备属于人」。** 现有的一次性配对码加设备令牌机制保留，令牌记录上加
  一个 `user` 字段。管理员 `user add alice` 发一个绑定到她的码，她粘一次，这台设备从此
  就是她。界面上把它呈现成「输入邀请码」。
  - 理由：多用户需要的是身份，不一定需要密码。密码贵的不是校验，是哈希、改密、找回、
    暴力破解防护这些周边。
  - 代价：没有自助，换电脑要找管理员再要一个码。对有管理员的组织工具，这可审计。
- 用户 id 复用原租户 slug 规则 `[a-z][a-z0-9-]{1,30}`。
- **联系人就是这台主机的用户列表。** 界面上不做邀请流程。单机桌面版没有组织，联系人为空，
  但仍然可以建群（我和我的几个 agent）。
- **权限不做区分，人人都是管理员**，包括修改 provider。已知的尖角：改 endpoint 等于把
  全组织的提示词转走，手滑就会发生。密钥读回来是掩码，写没有拦。

## 2. Provider

全局一份，不按人区分。这已经是现状——settings 是 Runtime 全局的。已知缺口：没有按人计量，
并发闸限的是并行度不是总量，一个人可以在额度上把全组织烧穿。先不做。

## 3. Agent：定义、实例、模板

- **模板库加入即复制。** 用户把一个模板加进联系人，从此归他私有；模板之后的改动不追溯。
- **定义与实例分开。** 同一个定义可以有多份实例：**私聊的实例挂用户，群聊的实例挂群**。
  每份实例有自己的桌面、自己的队列、自己的会话。
- **`tools` 被 `skills` 取代。** 不再按 agent 限制工具——研究员本身也要写报告、抓网页，
  原来的只读是错的。能力差异靠 skill 表达，所以内置工具列表要保持精简。
- 默认扩展一律走 skill，不新增 tool。

## 4. 消息与队列

- **一个 agent 眼里只有「我」和「非我」。** 群里有几个人不重要，用户信息只用来定义对话
  顺序和展示。
- **每实例一条队列、一个执行位**，一次只处理一条消息。头像上显示队列深度。执行位挂在
  实例上，不挂在定义上——否则全组织在同一个 agent 上排成一队。
- **被 @ 才醒。** 每个实例在每个会话里记一个读指针；醒来时把指针之后发生的事情作为
  delta 补进去，framing 是「环境发生了这些变化」，不是「有人对你说话」。
- **delta 过长先摘要再投**，用被 @ 的那个 agent 自己的模型。
- 压缩仍由 agent 自己的 runtime 控制。

## 5. 群聊

- **真 @ 和文本 @ 分开。** 真 @ 是消息里的结构化提及块，由一个能往会话发消息的 CLI 产生，
  skill 通过 bash 调它。模型在正文里打的任何 @ 都只是文本，不路由。
- **群助理就是默认助理**，每群唯一，不可更换，活跃/静默的开关点在它身上。
- **只有群助理拿得到那个发消息的 skill。** 这是防死循环的唯一不变式——人可以 @ 任何 agent，
  agent 只有群助理能 @ 别人，agent @ 人只产生通知不唤醒。
  - 依据：Buzz 有过一次真实事故，「每轮必须发言」加「完成委派必须 @ 委派者」两条规则
    组合成永动机，21 层互相「收到」。
- **同事说完话会唤醒活跃的群助理**，它自己说话不唤醒自己。这一条是编排的前提：
  「A 做完，把结果给 B」之所以成立，是因为群助理能知道 A 回来了。扇出仍然只有它一个出口，
  但深度需要另一道闸——**一个群在没人说话的情况下最多自己走 12 步**，走到头它自己停下来
  报一句，等人再开口才继续。上面那次事故里缺的正是这道闸。
- 群里也做人和人之间的私聊与对话，会话模型必须支持一个 agent 都没有的会话。

## 6. 工作区与资产

- **目录挂 agent 实例**，文件跨会话留着。
- **资产视图挂会话**，只列这次会话的上传和产物。所以「新话题就是新工作区」在用户眼里成立，
  实现上不用搬文件。
- **交接就是转发即复制**：把选中的消息和文件做成一张可预览、agent 读得懂的卡片发过去。
  不冻结、不做授权、不做撤销。

## 7. 记忆

两层：

- **共有层**跨用户累积，是 agent 自己的手艺——「我做这类任务容易在哪儿栽」。
  **只写方法论，不写事实**：不出现人名、公司、文件名、数字、项目名。
- **对人层**存各用户目录下，是偏好和背景。
- **群实例只用共有层**，不碰任何人的对人层。否则某人的记忆文件要挂进群沙箱，同群其他人
  就读得到。

记忆走成长记忆 skill，不走 memory 工具——现有的 memory drawer 工具、`memory.drawer` RPC
和设置里的 Memory 面板都删掉。每个 agent 默认带这个 skill。

约束是**指令级的，不是强制的**：判定一条经验算方法论还是算事实的是模型自己。记忆是
markdown，人随时能翻能删。

### 落地时改的一处

成长记忆最后没有落在文件系统上。文件工具会把路径限制在自己的桌面内
（`ToolContext.resolve` 解析软链后再判 `is_relative_to(cwd)`），所以「共有层挂进每个桌面」
用软链做不到。改成 `aeloon-runtime memory add/show` 这个 CLI 加一份 skill，
Runtime 把两层拼进这位同事自己的 instructions。好处是「群实例只拿共有层」由 Runtime 决定，
不再靠目录挂载碰运气。

## 8. 隔离：先不做，但这是对外部署的准入条件

现在的内置工具明确不是沙箱——`bash` 继承 Runtime 进程的 uid、环境和文件系统。一个进程
服务整个组织时，任何用户的 agent 一条 `bash` 就能读到 `config.json` 里组织唯一那把
API key，以及 `runtime.sqlite` 里全组织的消息。

**没有轻量版**：只要 bash 不受限，文件层面的任何限制都是装饰。看起来便宜的那档（把工具
子进程降权到另一个 OS 用户）需要同样的架构改动——执行、取消、流式输出都要跨进程边界，
只省下做镜像那部分。

**结论**：先不做。判据是——**只要部署给「互相之间不该看到对方东西」的人，就必须先做。**
自己用或者给本来就共享一切的小团队用，不加没问题。

做的时候的形态：

- 只有动手的部分进沙箱：bash、文件读写、grep/find/ls、Office 技能脚本。推理、密钥、
  会话状态、身份都留在 Runtime 里——agent 连模型调用都不是自己发的，拿不到密钥。
- 带凭据出网的工具（`web_search`/`web_fetch`）留在 Runtime，不进沙箱。
- **沙箱边界就是桌面的归属边界**：私聊实例跑在用户沙箱，群实例跑在群沙箱。
- 生命周期倾向**每轮一个**：开销摊到一轮里、每轮干净、轮末自动收掉 agent 留下的后台进程，
  边界正好落在「取消时杀进程组」这个已有的语义上。
- 隔离强度来自挂载和命名空间，不来自一次性。`bash` 本来就没有持久 shell（每次调用起一个
  新进程），所以一次性沙箱在行为上和现在等价。
- 挂载只覆盖文件这一维：网络（容器默认能出网）和资源（cgroup 限额）要另外管。

## 9. 并发

三层，各管各的：

- **全局上限**：这台机器同时跑几个操作。天花板是真实内存和模型侧速率限制——每个并发操作
  是一个 SessionAgent 加一个 provider 客户端，再加它派生的子进程（Office 技能要拉
  LibreOffice，很重）。
- **每用户上限**：一个人最多同时占几个执行位。防的是一个人跑八个任务把全组织饿死，
  和信任无关，很便宜。**这一层落在第 3 段做**：会话要先挂到人身上才有得数，
  在实例出现之前建这个闸门只会得到一个恒等于 owner 的空壳。
- **每实例一个执行位**：产品语义，写死不配置。今天已有等价物——每会话一把锁。

## 10. 实施顺序

1. **落地当前重构**：三个仓库的现有提交移到 `future`；UI 三点（历史折进右上、新会话按钮
   在右上、默认开上次选择的对话）；agent 定义 `tools` 换 `skills`；摘掉 lock 校验；这份文档。
2. **用户与鉴权**：Runtime 引入 user，设备绑 user，配对码按人发；用户管理 CLI 与界面；
   删掉 tenant 与网关 slug 路由。每方法授权与每用户并发闸推到第 3 段——两者都要先有
   「这个会话属于谁」。
3. **会话、消息与队列**：会话模型与成员；结构化提及块；定义与实例拆分；每实例队列与执行位；
   读指针、delta、超长摘要；群助理与它的发消息 CLI。界面上是侧栏「单聊 / 群聊」两个页签、
   一个房间视图（成员条、消息流、@ 选择器），以及 `message.created` 与
   `thread.members_changed` 两个事件——头像上的排队徽标就是从后者来的。
4. **模板库、skill 市场与记忆**：成长记忆双层（已做，走 skill + CLI，不走 memory 工具）；
   转发卡片（`message.forward`，已做）；skill 市场与模板库留在 UI 侧——
   Runtime 已经有它们要的数据（`catalog.get` 列 skill，`agent.*` 管定义），
   现在再加一层 `template.*` 只会得到一个空目录：内置的四位同事本来就是「加入即复制」。

沙箱不排在这四段里，作为对外部署前的准入条件单独挂着。

### 现状（2026-09-08）

第 1、2、3 段都已经落在三个仓库的工作区里，第 4 段的 Runtime 侧也做完了，只剩 skill 市场
和模板库两个界面。两处已知缺口：

- **每方法授权还是没做。** `thread.list` 和 `system.snapshot` 不按人过滤，同一台机器上的人
  互相看得到对方的会话。归属信息已经有了（`members` 表加实例的 owner），缺的是闸门本身。
- **界面里只能看人，不能增删人。** 联系人读 `user.list`，发码和移除仍然只有 CLI 有。

## 11. 流程

不合 main，全部落在 `future`。**不发发行版，直接用源码构建测试。** 因此
`runtime-bundle.lock.json` 的校验从 `bun run check` 里摘掉——不发版之后它永远校验一个
过期的锁。
